## PR 1 — `phase-oem-seed-prod`

### Goal

Get the OEM catalog into the live database so PR 2-4 have something
to work with. No code changes — just running the migration + the
three seeds that already exist on `phase-oem-catalog`.

### Locked decisions

- **Migration goes through `supabase-dev` first** (project
  `iuimkzettrrqvvvgfvqp`). Production has 0 products / 0 sales so an
  additive-only migration is low-risk, but dev is still the smoke
  target.
- **Run all three seeds against dev** to verify counts:
  - eParts: 376 machines · ~2,226 revisions · ~48,315 components · ~28k unique parts
  - PDF: 365 machines (separate rows from eParts because `(code, source)` is the unique key) · ~6,676 components · ~25k unique parts
  - PartPriceSnapshot: ~200k rows
- **Order of seeds doesn't matter.** They write to different tables
  (or different rows in the same table, keyed by source).
- **Regenerate `prisma/draft/wn_parts_export.json`** before running
  `seed-oem-pdfs.ts` — the file is gitignored and must be fresh from
  the SQLite.
- **Push to prod via Railway deploy** of the merged branch — Railway
  runs `prisma migrate deploy` automatically. Then re-run the seeds
  locally pointing at prod `DATABASE_URL`.

### Execution order

1. Wake the dev Supabase project (open its dashboard) — paused projects
   take ~2 min to come back. Verify with a trivial `SELECT 1`.
2. Set `DATABASE_URL` to the dev pooler URL.
3. `npx prisma migrate deploy` — applies `20260623100000_phase_oem_catalog`.
4. Verify five new tables exist:
   ```sql
   SELECT table_name FROM information_schema.tables
   WHERE table_schema = 'public' AND table_name LIKE 'Oem%' OR table_name = 'PartPriceSnapshot';
   ```
5. Regenerate the PDF export:
   ```bash
   python prisma/draft/export_wn_sqlite.py \
     --db "data/wn_parts.sqlite" \
     --out prisma/draft/wn_parts_export.json
   ```
6. Run all three seeds (any order; sequential is fine):
   ```bash
   npx tsx prisma/seed-oem-eparts.ts          # ~5-10 min
   npx tsx prisma/seed-oem-pdfs.ts            # ~1-2 min
   npx tsx prisma/seed-part-prices.ts         # ~2-3 min
   ```
7. Spot-check counts:
   ```sql
   SELECT source, COUNT(*) FROM "OemMachine" GROUP BY source;
   SELECT COUNT(*) FROM "OemMachineRevision";
   SELECT COUNT(*) FROM "OemComponent";
   SELECT COUNT(*) FROM "OemPart";
   SELECT retailer, COUNT(*) FROM "PartPriceSnapshot" GROUP BY retailer;
   ```
8. If dev counts match the expected ranges above → push the branch +
   PR + merge to main. Railway deploys → migration auto-applies.
9. Run the three seeds again against prod `DATABASE_URL`.

## PR 2 — `phase-oem-render-diagrams`

### Goal

Two things, both batch jobs, no app code change:
1. Render the missing PDF diagrams (5,000-8,000 PNGs) for the 348
   PDF-derived manuals that have no `drawings/<slug>_p<NN>.png` file
   today.
2. Upload all diagram assets — both rendered PDF PNGs and the eParts
   API HD PNGs + `.hd3` files — to Supabase Storage. Switch
   `OemComponent.diagramImageFilename` from local-path to storage key.

### Locked decisions

- **Bucket name: `oem-diagrams`.** Private, signed-URL access. Same
  pattern as the Phase 4.5 `backups` bucket — auto-create idempotently.
- **Storage layout:**
  ```
  oem-diagrams/eparts/{filename}                  ← API HD PNGs
  oem-diagrams/eparts/{filename}.hd3              ← (also upload .hd3 alongside; PR 4 needs them)
  oem-diagrams/pdf/{machineCode}/{slug}_p{NN}.png ← PDF-rendered
  ```
- **Render at 200 DPI** (was 150 in `render_diagrams.py`). The viewer
  in PR 4 will zoom; 200 DPI is the sweet spot between file size and
  legibility for fastener callouts.
- **Schema column stays `diagramImageFilename`.** No new column. The
  storefront builds the signed URL at request time from the storage
  key. After this PR, the value is `eparts/WWMEX...png` rather than
  `WWMEX...png`.
- **`hotspotsJson` stays inlined on the row** — no change. The hd3
  file in Storage is for fallback / debugging only.
- **Local copies stay** on the dev machine until the storage upload
  is verified end-to-end. Don't `rm -rf eparts_assets/` until you've
  signed-URL-fetched at least 10 random rows and rendered them in a
  browser.

### Files

```
data/render_pdf_diagrams.py     ← new, batch-render the 348 manuals
data/upload_oem_assets.py       ← new, upload eparts_assets/ + drawings/ to Storage
prisma/migrations/20260624000000_oem_diagram_storage_key/  ← optional, only if we add an indexed bucket column
src/lib/oem/diagram-url.ts                     ← new, signed-URL helper
```

### Step-by-step

1. **PDF render pass.** New `render_pdf_diagrams.py`:
   - Walk SQLite `assembly_groups` rows
   - For each row where `drawing_file` is set but the file doesn't
     exist on disk: open `pdfs_shop/<source_pdf>` via `fitz`, render
     `diagram_page` at 200 DPI, save to `drawings/<slug>_p<NN>.png`
   - Resumable (skip files already present)
   - Expected output: 5,000-8,000 new PNGs, ~1-2 GB
2. **Upload pass.** New `upload_oem_assets.py` (Python — psycopg2 +
   supabase-py, or node — `@supabase/supabase-js`):
   - Create bucket `oem-diagrams` if missing
   - For each file in `eparts_assets/`: upload to `eparts/<filename>`
   - For each file in `drawings/`: upload to `pdf/<machineCode>/<filename>` (machineCode derived from the path)
   - Parallel uploads (10 concurrent), resumable (HEAD check before PUT)
   - Update `OemComponent.diagramImageFilename` in batch to the storage key
3. **Signed-URL helper.** `src/lib/oem/diagram-url.ts`:
   ```ts
   export async function getDiagramUrl(storageKey: string, ttlSeconds = 3600) {
     const { data, error } = await supabaseAdmin.storage
       .from("oem-diagrams")
       .createSignedUrl(storageKey, ttlSeconds);
     if (error) throw error;
     return data.signedUrl;
   }
   ```

### Gates

Same four. Plus a manual sample: download 10 random `OemComponent`
rows, fetch each signed URL, confirm PNG renders in a browser.

### Risks

- **Storage cost.** 575 MB API + ~1-2 GB rendered = ~2 GB. Supabase
  free tier is 1 GB Storage. Pro tier ($25/mo) is 100 GB. Plan a paid
  tier before this PR, or skip the PDF render upload and serve PDF
  diagrams from the app process directly (less ideal).
- **Render quality on giant PDFs.** RC110-class books have 400+ pages
  and the renderer may OOM. Cap concurrency to 1 and run sequentially.

## PR 3 — `phase-search-oem-number`

### Goal

A customer pastes an OEM part number into the storefront search bar
(`/`, `/produkter`, anywhere). The result page shows either:
- The matching Dyvika `Product` (cart-ready), OR
- A "We don't carry this part yet" card with a "Be om pris" CTA that
  pre-fills the part number into the existing `Quote` form.

The match is OEM `partNumber` ↔ Dyvika `Product.partNumber` OR any
entry in `Product.replacesPartNumbers[]`.

### Locked decisions

- **No new search index.** The OEM catalog tables stay admin-side
  reference data. We don't extend `Product.searchKey` / `searchVector`
  to include OEM SKUs from `OemPart`. The match runs as a separate
  query at search time, AFTER the existing Phase 5 three-stage cascade
  fails to return Dyvika `Product` rows.
- **Match logic:** exact OEM number first, then case-insensitive +
  punctuation-stripped. No fuzzy matching (false positives are worse
  than misses for OEM lookups).
- **"Be om pris" prefill.** The new card includes a form that posts to
  the existing `createQuoteAction` with `notes = "OEM lookup: {partNumber}"`.
  Reuses the v4.2 PR 3 `QuoteForm` component if available.
- **PartPriceSnapshot is NOT exposed.** Customer-facing search doesn't
  reveal what competitors charge. That's admin-only (Phase 4 here).

### Files to create

```
src/lib/oem/lookup.ts                          ← exact + normalized OEM lookup
src/components/search/OemFallbackCard.tsx      ← "we don't carry this" + Be om pris CTA
src/app/[locale]/(customer)/sok/page.tsx       ← new search results route (if not already there)
```

### Files to modify

```
src/components/search/SearchBar.tsx            ← chain OEM lookup after the existing FTS miss
src/app/actions/search.ts (or wherever)        ← add the OEM-match branch to the server-side search response
messages/nb.json                               ← new strings: "Vi fører ikke denne delen ennå", "Be om pris", etc.
```

### Step-by-step

1. **Lookup helper** `src/lib/oem/lookup.ts`:
   ```ts
   export async function findOemPart(rawNumber: string) {
     const normalized = rawNumber.replace(/[\s\-_.]/g, "").toUpperCase();
     // Try exact first, then normalized
     const exact = await prisma.oemPart.findFirst({
       where: { partNumber: rawNumber },
       select: { partNumber: true, partName: true, component: { select: { name: true, revision: { select: { revision: true, machine: { select: { code: true, name: true } } } } } } },
     });
     if (exact) return { kind: "exact" as const, oemPart: exact };
     // Match a Dyvika Product that lists this number as a replacement
     const product = await prisma.product.findFirst({
       where: {
         OR: [
           { partNumber: rawNumber },
           { replacesPartNumbers: { has: rawNumber } },
         ],
         isActive: true, isDiscontinued: false,
       },
     });
     if (product) return { kind: "product" as const, product };
     // Last resort — normalized OEM match
     // ...
     return { kind: "none" as const };
   }
   ```
2. **Search-results page** — if `findOemPart()` returns `product`,
   redirect to `/produkter/<sku>`. If `oemPart` (no Dyvika match),
   render `<OemFallbackCard partNumber={n} oemContext={...} />`.
3. **The fallback card** shows: the OEM partName + which machine it
   fits ("Fits BPU 3050A US, Vibration Plate"), a "Be om pris" form
   button that pre-fills the part number + machine + component, and a
   "Look up another part" input.

### Gates + smoke

Standard four gates. Manual smoke:
- Paste `5000216582` (an OEM Axle for BPU 3050A US) into SearchBar →
  fallback card with machine context + Be om pris CTA
- Paste a number that's both an OEM part AND a Dyvika `Product.partNumber`
  → redirect to the PDP
- Paste a fake number `9999999999` → existing "no results" page
- Submit the Be om pris form → new `Quote` row in `/admin/tilbud` with
  the part number in notes

### Risks

- **Lots of "we don't carry it" outcomes.** ~52% of OEM SKUs aren't in
  any retailer scrape; even fewer match a Dyvika `Product` today. The
  fallback UX needs to be encouraging, not dead-end-feeling.
- **Duplicate matches.** Same OEM number can appear under multiple
  machines / revisions. Just pick the most recent and link to the
  parts viewer (PR 4) from the fallback card so the customer can see
  the full context.

## PR 4 — `phase-parts-viewer`

### Goal

A public interactive parts viewer at
`/oem/<machineCode>/<revision>/<componentCode>`. Renders the HD PNG
diagram with clickable callout hotspots that highlight matching rows
in the parts table, and vice versa. Each parts table row shows the
OEM number, name, quantity, and a "Kjøp hos Dyvika" link when there's
a matching Dyvika `Product`, otherwise a "Be om pris" inline button.

### Locked decisions

- **URL pattern:** `/oem/<machineCode>/<revision>/<componentCode>`.
  Public (no login). Indexed by search engines — every OEM part page
  is a SEO entry.
- **Drilldown navigation:** `/oem/<machineCode>` shows the catalogue
  card + revision selector + component grid. Pick a component → land
  on the viewer URL. Wacker Neuson eParts UX as the reference.
- **Diagram rendering:** absolute-positioned `<button>` elements over
  the PNG at `(x1,y1)→(x2,y2)` from `hotspotsJson.definition.rectangle[]`.
  Coords scale from `hotspotsJson.img[1].{width,height}` (the HD size).
- **Bidirectional highlight:** hover/click hotspot → highlight row;
  hover/click row → highlight hotspot. Same Zustand pattern as the
  drawer state machine (small store: `{ activeCallout: string|null }`).
- **Empty hotspots:** rows for PDF-source components have no `hotspotsJson`
  — table-only view, diagram is just an image. No degraded UX banner;
  just no clickable overlay.
- **Cross-link to Product:** each row resolves
  `OemPart.partNumber → Product` via the lookup helper from PR 3. If
  matched: row shows price + "Kjøp" button. If not: "Be om pris"
  inline button (same QuoteForm prefill as PR 3).

### Files to create

```
src/app/[locale]/(customer)/oem/[machineCode]/page.tsx
src/app/[locale]/(customer)/oem/[machineCode]/[revision]/page.tsx
src/app/[locale]/(customer)/oem/[machineCode]/[revision]/[componentCode]/page.tsx
src/components/oem/MachineCard.tsx              ← header with categoryPath breadcrumb
src/components/oem/RevisionSelector.tsx         ← dropdown + "Show in: 108, 107, 106..."
src/components/oem/ComponentGrid.tsx            ← thumbnails of components per revision
src/components/oem/PartsViewer.tsx              ← the diagram + table component
src/components/oem/DiagramWithHotspots.tsx      ← positioned-button overlay
src/components/oem/PartsTable.tsx               ← rows with Dyvika cross-link or Be om pris
src/lib/oem/queries.ts                          ← server queries (getMachine, getComponent, etc.)
src/lib/oem/active-callout-store.ts             ← Zustand store
```

### Step-by-step

1. **Server queries** in `src/lib/oem/queries.ts`:
   - `getMachine(code)` → OemMachine + revisions[] + counts
   - `getComponent(code, rev, componentCode)` → OemComponent + parts[] + each part with Dyvika `Product` resolved (left join via `partNumber` + `replacesPartNumbers`)
   - All cached via `'use cache'` + `cacheTag("oem-machine-<code>")` (same pattern as v4.2 PR 1 categories cache).
2. **Drilldown pages** — three nested routes. Server components,
   render directly from `getMachine` / `getComponent` results.
3. **PartsViewer** — client component. Initialises the Zustand store
   with `activeCallout = null`. Renders:
   - `<DiagramWithHotspots>` — PNG via `<Image>` (next/image, sized
     from `hotspotsJson.img[1]`), absolute-positioned `<button>` for
     each rectangle, classes flip based on `activeCallout === id`.
   - `<PartsTable>` — rows keyed on callout. `onMouseEnter / onClick`
     sets `activeCallout`.
4. **PNG signed URLs** — use the helper from PR 2. Cache the URL on
   the server response so the page doesn't hit Storage on every render.
5. **Be om pris inline** — reuses the QuoteForm shell from PR 3, but
   prefilled with the full context (machine, component, callout).

### Gates + smoke

Standard four. Manual smoke (after PR 1-3 land):
- `/oem/5000610361` — BPU 3050A US machine card, 9 revisions visible
- `/oem/5000610361/108` — component grid for rev 108 with 10
  top-level + 18 engine sub-components
- `/oem/5000610361/108/5004907113` — Vibration Plate viewer. PNG +
  19 callouts. Click callout #3 → row "Axle (5000216582)"
  highlights. Click row "Cylindrical roller bearing" → callout #2
  highlights on diagram.
- For each parts row: at least one of (Dyvika "Kjøp" button) or
  (Be om pris inline button) renders.
- `/oem/5000610361/108/5004907113` with screen reader — callouts
  have aria-labels matching their part name.

### Risks

- **Image scaling.** `hotspotsJson.img[1]` gives the HD canvas size.
  The browser may render the PNG at a smaller display width. The
  hotspot overlay needs to scale rectangles proportionally — store
  coords as percentages of the canvas, not absolute pixels.
- **Mobile UX.** Click hotspots are small at desktop scale (~20 px
  squares). On mobile, the diagram has to scroll horizontally to keep
  the hotspots tappable. Plan for pinch-to-zoom + a vertical-stack
  parts-list layout on `< md`.
- **SEO indexing the whole catalog.** ~50k OEM part pages potentially
  index-bombing the site. Add a sensible `robots.txt` directive and a
  canonical-URL strategy (only the most-recent revision per machine is
  indexed; older revisions noindex).
