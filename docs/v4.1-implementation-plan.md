# IndustriParts — v4 → v4.1 Implementation Plan

> Single source of truth for the v4 → v4.1 upgrade work and the urgent site bug
> triage. Source spec: [industriparts-spec-v4.docx](industriparts-spec-v4.docx)
> (v4.1, May 2026).

## How to use this document

Order of execution:

1. **Phase 0** — Site triage. Fix the live site (logout, dead links) before any
   new feature work. The site does not currently work end-to-end; nothing else
   matters until that is true.
2. **Phases 1–9** — The v4.1 sprints, in the order listed. Each phase is gated
   by its predecessor's "Definition of done" section.
3. **Architectural conventions** — Apply continuously across all phases. They
   are not their own sprint.
4. **Decisions required** — Read this section before starting any phase. Some
   need user input.

This plan is a living document. Update it as facts change.

## Always-on rules

These apply to every change in every phase.

1. **Read Next 16 docs before introducing a new framework concept.** Per
   [AGENTS.md](../AGENTS.md), this is not stock Next.js. Check
   `node_modules/next/dist/docs/` for the relevant page first. Same for Prisma
   7 changes.
2. **No emojis in code or files** unless the user explicitly asks for them.
3. **No backwards-compatibility hacks.** When refactoring, delete old code
   instead of leaving "removed" markers, dead exports, or rename shims.
4. **No new comments unless the WHY is non-obvious.** Identifiers should
   carry the meaning; comments are reserved for hidden constraints,
   surprising behaviour, or workarounds with a citation.
5. **Server Actions get zod input validation** from this point forward. Old
   actions are retrofitted in their domain's sprint.
6. **Decimal stays Decimal** until the presentation layer. Converting to JS
   `number` mid-flow is the bug pattern Phase 2 is built to fix.
7. **Money crosses process boundaries in øre.** Vipps API, KID, BullMQ jobs,
   and AuditLog all use the smallest unit. Decimal kroner is for the DB and
   the UI.
8. **Every webhook handler opens with an idempotency check.** Once the
   `WebhookEvent` table lands in Phase 1, it is the canonical mechanism. Until
   then, the existing AuditLog string-action check stays.
9. **Tests are required for the money path.** Pricing, KID, modulo-11,
   batch-slot determination, stock-reservation race, webhook idempotency.
   Other tests are nice-to-have.
10. **Branch model:** `main` deploys to production. `staging` deploys to a
    Supabase branch + Railway preview. Never push directly to main.

## Phase 0 — Site Triage (Debug Plan)

**Goal.** Every link on the site goes somewhere real. Logout logs the user out
and lands on a real page. A regression test prevents this from recurring.

**Effort.** 3–5 dev-days.

**Why first.** The user reports that clicking Logout takes them to a non-
existent page and does not log them out, and that "a lot of other links are
leading to pages that does not exist." Adding new features on top of broken
navigation will compound the problem. Fix the floor before adding more
furniture.

### Confirmed targets from live-site walkthrough (May 2026)

A live walkthrough of the production site has already identified the
following concrete 404s. D0.1 should still run a complete audit, but
these are guaranteed targets:

| Symptom | Root cause hypothesis |
|---|---|
| `/konto` returns 404 | Page never built. `Min konto` link in header points at it. |
| `/kasse` returns 404 | Page never built. Cart's `Til kassen` button points at it. **Checkout is fully broken — blocks every purchase.** |
| `GET /api/auth/logout` returns 404; session stays alive | Route handler exports POST only (or nothing); header link is `<a href>` which is a GET. Fix: replace with a Server Action triggered by a `<form>` POST. |
| `/login` renders chrome but no form when authenticated | Auth-redirect logic probably runs server-side but is silently failing under Next 16. Verify in [src/app/[locale]/login/](../src/app/[locale]/login/). |
| `/registrer` same as `/login` | Same pattern. |
| `/betaling/bekreftelse` renders empty | Needs `?saleId=…` URL param or referrer; without context it has nothing to show. Either render a "no order context" message, or 404 cleanly. |

Feature gaps surfaced by the walkthrough but **not** linked from any
existing UI (so they are spec items rather than dead links — handled in
later phases):

- `/admin/brukere` (user/role admin per spec §16, SUPER_ADMIN only)
- `/admin/fakturaer` (invoice list per spec §16)

### D0.1 — Discovery (half day)

Static link audit. Write `scripts/audit-links.ts` that:

- Walks `src/app/[locale]/`, `src/components/`, `src/lib/`, `src/messages/`.
- Greps for `href="/...`, `<Link href={...`, `redirect("/`,
  `router.push("/`, and `<form action="...`.
- Extracts every internal route reference.
- Cross-references against the actual `src/app/[locale]/.../page.tsx` file
  layout.
- Reports every reference where the target page does not exist.

Output: `docs/audit/dead-links-YYYY-MM-DD.md` listing every broken reference,
its source file, and a triage decision column.

### D0.2 — Logout fix (half day)

Symptom: Logout button leads to a 404 and does not actually log out.

Diagnosis order:

1. Read [src/components/layout/StoreHeader.tsx](../src/components/layout/StoreHeader.tsx)
   (and any admin header) — find the Logout link or button. What does it
   actually point at?
2. Confirm [src/app/api/auth/logout/route.ts](../src/app/api/auth/logout/route.ts)
   exists and handles POST.
3. Check the locale prefix. The spec specifies `localePrefix: 'never'` —
   routes must not be prefixed with `/nb/`. If the Logout link points at
   `/nb/api/auth/logout` that is the bug.
4. Verify `supabase.auth.signOut()` is actually called and all `sb-*`
   cookies are expired.
5. Verify the final redirect target (`/` or `/login`) exists and renders.

Most likely fix: rebuild the logout flow as a Server Action that calls
`supabase.auth.signOut()`, expires cookies, then `redirect('/')`. The current
API route may not be wired correctly under Next 16 + next-intl.

### D0.3 — Fix discovered dead links (1–2 days)

Walk the D0.1 output. For each broken reference:

- **If the page is supposed to exist per spec but does not:** stub it with a
  "Kommer snart" placeholder page so the link no longer 404s, and add it to
  `docs/route-stub-registry.md` so it is tracked as "to build".
- **If the page should never have been linked:** remove the link.
- **If the page exists at a different path:** update the href.

Triage priority:

1. StoreHeader navigation (everyone hits it)
2. Admin sidebar
3. Login / register / glemt-passord flow
4. Cart and checkout flow
5. Email templates
6. Footer

### D0.4 — Regression test (half day)

Add `e2e/link-integrity.spec.ts`:

- Logs in once as SUPER_ADMIN and once as guest.
- For each role, visits every page in a known list (admin sidebar +
  storefront top-level).
- Asserts every page returns 200 and contains the expected heading.
- Walks every visible link on those pages and asserts each target also
  returns 200.

This runs in CI from this day forward. Blocks merge on any 404 or 500.

### D0.5 — Manual smoke on staging (half day)

Once D0.1 through D0.4 are merged: deploy to staging, manually click through:

- Login → / → /produkter → /produkter/[sku] → /handlekurv → /kasse →
  Vipps test redirect.
- /admin → every sidebar item → back to dashboard.
- Logout from each page.

Document remaining issues, fix them, repeat until clean.

### Definition of done — Phase 0

- Zero 404s found by the link smoke test.
- Logout works: clicking it logs the user out and lands on `/`.
- Playwright link smoke test runs in CI on every PR.
- Outstanding non-spec'd routes are tracked in
  [route-stub-registry.md](route-stub-registry.md).

## Phase 0.6 — Dynamic category management

**Goal.** Categories become a live, editable taxonomy that grows as new
products are added. Both manual product creation and CSV import can
declare a category by name; if it does not exist, it is created. An admin
page exists to view and edit the tree.

**Effort.** 1–2 dev-days.

**Why now.** The new drawer (Phase 0.5) drilldown is only useful with a
real category tree behind it. Today the tree is **static** — it is
populated only by the seed file, with no admin UI and no auto-create
logic. Confirmed by reading the code:

- [src/app/actions/product.ts:47](../src/app/actions/product.ts) accepts
  an optional `categoryId` and writes `categoryId || null`. No lookup,
  no create.
- [src/app/[locale]/admin/produkter/ny/_NyttProduktForm.tsx:292](../src/app/[locale]/admin/produkter/ny/_NyttProduktForm.tsx)
  renders a flat `<select>` of existing categories. No nesting, no
  create-new option.
- [src/app/actions/product-import.ts:69](../src/app/actions/product-import.ts)
  resolves a `categorySlug` column against a pre-loaded map; **misses
  silently fall back to `null`** — products import as uncategorised
  without warning. No create.
- No `/admin/kategorier` page or `createCategory` server action exists
  anywhere in `src/`.

### Deliverables

- New server actions in `src/app/actions/category.ts`:
  - `createCategoryAction({ name, parentSlug? })` — slugifies the name,
    enforces uniqueness, sets `displayOrder` to next-in-parent.
  - `findOrCreateCategoryByPath(path: string)` — accepts a
    slash-separated path like `verktoy/elektroverktoy/borrmaskiner`,
    walks the tree, creates each missing segment under the prior parent,
    returns the leaf id. **Pure idempotent.**
  - `updateCategoryAction`, `deleteCategoryAction` (refuses delete if
    the category has products or children — admin must move them first).
  - `reorderCategoriesAction` — drag-to-reorder in the admin UI.
- Update [src/app/actions/product.ts](../src/app/actions/product.ts)
  `createProductAction`:
  - Accept `categoryPath?: string` alongside the existing
    `categoryId?: string`.
  - If `categoryPath` is provided and resolves via
    `findOrCreateCategoryByPath`, it wins over `categoryId`.
- Update [src/app/actions/product-import.ts](../src/app/actions/product-import.ts):
  - Replace the `categorySlug` column with `categoryPath`. Slug column
    stays accepted for backwards compatibility.
  - On miss, `findOrCreateCategoryByPath` rather than silent `null`.
  - Import summary reports number of categories auto-created and the
    paths of any that were created, so the admin can review.
- Replace the `<select>` in
  [`_NyttProduktForm.tsx`](../src/app/[locale]/admin/produkter/ny/_NyttProduktForm.tsx)
  with a new `CategoryPicker.tsx` component:
  - Combobox with type-ahead over existing categories.
  - Shows the full path of each match (e.g. `Verktøy / Elektro / Borr`).
  - When the typed string does not match an existing category, shows a
    "+ Opprett kategori" option that triggers a small inline form for
    parent selection and confirms before creating.
- Same picker on the product edit page
  (`/admin/produkter/[sku]/rediger`).
- New admin page `/admin/kategorier`:
  - Tree view of all categories with product count per node.
  - Drag-to-reorder within a parent.
  - Inline rename, change-parent (move), and delete (with the
    refuse-if-non-empty rule).
  - "Legg til kategori" button at any level.
- Update [prisma/seed.ts](../prisma/seed.ts) so the seed list is the
  initial state, not the only state. Re-running seed must not duplicate
  existing categories.

### Schema migration

None — the existing `Category` model already supports nesting via
`parentId`. Only `displayOrder` is used; we may add a `description String?`
field if the admin page wants help text.

### Tests required

- Unit: `slugify` produces stable Norwegian-friendly slugs (æ → ae,
  ø → o, å → a).
- Unit: `findOrCreateCategoryByPath` is idempotent; calling twice with
  the same path returns the same ids and creates nothing the second
  time.
- Integration: CSV import with `categoryPath="verktoy/nytt-segment"`

- Integration: deleting a category with children fails with a clear
  error code.
- E2E: admin types a new category name on the new-product form,
  confirms create, sees the product land in the new category in the

### Decision needed before coding

The category-path separator in CSV: **`/`** (recommended — readable,
collision-free with names) or `>` (also common, easier to scan in a
spreadsheet). Default: `/`.

### Definition of done — Phase 0.6

- A new manual product can be created with a brand-new category in one

- CSV import never silently drops a category — every product either
  resolves or auto-creates.
- `/admin/kategorier` is the source of truth for the tree.
- Storefront drawer (Phase 0.5) reflects the live tree without

## Phase 0.7 — Condition, provenance, fitment filters, My Machines

**Goal.** Products carry condition (new vs used + 5-level rating + free
notes) and provenance (Genuine / OEM / Aftermarket). Storefront listings
expose these as visible always-on filters, alongside brand and model
fitment filters. Logged-in users save favourite machines to "Mine
maskiner" and filter listings to those machines in one click.

**Effort.** 3 dev-days.

**Why now.** Condition and provenance are core attributes of an
industrial spare-parts catalogue; they need to be in the schema before
any meaningful product list (Phase 0.5 chrome) goes live. Storefront
filters reuse existing `ProductFitment` infrastructure with no backend
search dependency, so this phase ships fully before Phase 5.

### Schema migration

```prisma
enum ProductCondition {
  NEW
  USED
}

enum ConditionRating {
  AS_NEW         // Som ny — minimal use, no visible wear
  EXCELLENT      // Utmerket — light cosmetic wear, full function
  GOOD           // God — visible wear, full function
  FAIR           // Akseptabel — significant wear, full function
  POOR           // Slitt — heavy wear, function verified
}

enum PartProvenance {
  GENUINE        // Originaldeler
  OEM            // OEM-deler
  AFTERMARKET    // Uoriginale deler / Aftermarket
}

model Product {
  // ...existing fields...
  condition       ProductCondition @default(NEW)
  conditionRating ConditionRating? // required when condition = USED
  conditionNotes  String?
  provenance      PartProvenance   @default(AFTERMARKET)
}

model SavedMachine {
  id           String   @id @default(cuid())
  profileId    String
  modelId      String   // FK -> MachineModel
  label        String?  // user nickname, e.g. "Min EC380 fra 2022"
  serialNumber String?
  createdAt    DateTime @default(now())
  profile      Profile      @relation(fields: [profileId], references: [id], onDelete: Cascade)
  model        MachineModel @relation(fields: [modelId], references: [id])
  @@index([profileId])
  @@unique([profileId, modelId])
}
```

Validation rule (server-side, in pricing/product service):
`condition = USED` requires `conditionRating != null`. Enforce on every
write path; admin form refuses submit, CSV import row-level rejects with
clear error.

### Storefront filter UI (visible, not hidden)

New `ProductListingFilters.tsx` component, rendered above the product
grid on `/produkter`, `/kategori/[...slug]`, and `/sok` (search results).

Layout (top of grid, above the cards):

```
┌─────────────────────────────────────────────────────────┐
│ Tilstand:  [ Ny ]  [ Brukt ]                            │
│ Opphav:    [ Originaldel ]  [ OEM ]  [ Etter­marked ]   │
│ Merke:     [ Volvo ▾ ]      Modell: [ EC380 ▾ ]         │
│ Mine maskiner:  [ EC380 (2022) ]  [ Cat 320 ]    + Add  │
│                                                         │
│  Aktive filter:  [Volvo ✕]  [Brukt ✕]   [Tøm filter]    │
└─────────────────────────────────────────────────────────┘
```

Behaviour:

- Each chip is a toggle. Multi-select: nothing selected = no filter
  (all shown).
- Brand dropdown drives the Model dropdown — selecting Volvo restricts
  Model to Volvo models only. Both can be left blank.
- "Mine maskiner" row only renders for authenticated users with at
  least one `SavedMachine`. Each saved machine is a one-click filter
  that sets `makeId` and `modelId` together.
- Active filters appear as removable chips below the filter rows. X on
  each chip removes that single filter. **"Tøm filter"** button
  removes everything in one click.
- Filter state is **reflected in URL query parameters** so filters are
  bookmarkable, shareable, and survive the back button:

  ```
  /produkter?condition=USED&provenance=GENUINE,OEM&makeId=cm123&modelId=cm456
  ```

- Filter state survives between `/produkter` and `/sok` — a search
  inherits any active filter.

Server-side query (Prisma):

- `condition` filter: `WHERE condition IN (...)`.
- `provenance` filter: `WHERE provenance IN (...)`.
- `modelId` filter: `WHERE id IN (SELECT productId FROM ProductFitment WHERE modelId = ...)`.
- `makeId` filter (no modelId): `WHERE id IN (SELECT productId FROM ProductFitment WHERE modelId IN (SELECT id FROM MachineModel WHERE makeId = ...))`.
- All filters compose with `AND`.

   needing the more verbose "maskinprodusenten".

enum OrderStatus {

  PAID
  INVOICED
  REFUNDED         // new

## Architectural conventions (apply continuously)

These are the layered improvements identified in the architecture review.
They are not their own sprints; they are applied as you touch the relevant
code.

### A1 — Decimal discipline
Stop coercing Decimal to JS number. Lands via Phase 2.

### A2 — Service layer
Introduce `src/services/` organised by domain:
`services/orders/`, `services/inventory/`, `services/payments/`,
`services/billing/`, `services/catalog/`. Server Actions delegate to
services. Land incrementally as you touch each domain (Phases 3, 5, 7, 8).

### A3 — lib/ reorganisation
Move single-domain files from flat `src/lib/` to domain-grouped sub-folders
alongside services. Keep `src/lib/` for cross-cutting utilities only
(formatters, prisma client, supabase clients, logger, ratelimit).
Incremental, no big-bang.

### A4 — Drop generated/prisma path indirection
Prisma client output stays where it is, but stop importing enums via
`@/app/generated/prisma/enums` directly. Re-export from
`src/types/index.ts` and import from there. Migration: add re-exports
first, codemod imports gradually, eventually disallow direct imports via
ESLint rule.

### A5 — zod for Server Action inputs
Every new Server Action accepts zod-validated input. Existing actions are
retrofitted in their domain's sprint.

### A6 — OrderStatus expansion
Track full payment lifecycle via `Sale.status` alone. Don't infer from
AuditLog. Lands in Phase 3.

### A7 — WebhookEvent for idempotency
Stringly-typed AuditLog idempotency replaced. Lands in Phase 1.

### A8 — Result types for known business errors
Server Actions with known failure modes (insufficient stock, invalid promo,
etc.) return `{ ok: true, data } | { ok: false, error: 'CODE' }`
discriminated unions. Prisma exceptions still throw. Adopt as you touch
each action.

## Debugging method (apply to every fix)

For each new feature or bug fix:

1. Add a Sentry breadcrumb at the entry point.
2. Reproduce on staging if at all possible.
3. Add a failing test before the fix.
4. Make the test pass with the minimum change.
5. Run the full test suite locally.
6. If a regression is found post-merge, add the failing case to the test
   suite before fixing.
